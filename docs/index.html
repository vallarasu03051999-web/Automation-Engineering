01 Overview

One test file, six sequential test.step() blocks, one employee record taken from birth to deletion. The UI is driven through a Page Object Model (see structure); the API step mirrors the same record against a public test API so the scenario has something to cross-check against, since the demo site exposes no key-free REST API of its own.

Why an external API? OrangeHRM's real PIM API needs an authenticated session + CSRF token — there's nothing public to hit. Per the assessment's own suggestion, Step 4 simulates the "validate via API" requirement against ReqRes, a public test API that echoes back whatever it's sent, and asserts that echo matches what was just entered in the UI.

02 UI test flow

Six steps, run in order — each depends on the record the previous step created, so they execute as one continuous scenario rather than isolated tests.

1

Login

Submit Admin / admin123 on the login form.

asserts URL matches /dashboard/index "Dashboard" breadcrumb visible
2

Add employee

PIM → Add Employee. Fill first/last name and a generated Employee ID, upload assets/profile-picture.png, save.

asserts toast: "Successfully Saved" Personal Details shows the same Employee ID
3

Edit — Job Title & Employment Status

Search the employee list by Employee ID, open the record, switch to the Job tab, change both fields on the custom OrangeHRM dropdown widgets, save.

asserts toast: "Successfully Updated" fields display new values
4

Validate via API

PUT the same job title / employment status to the mirrored API record, then reload the Job tab to prove the UI change survived a fresh read, not just local component state.

asserts API payload = UI values values persist after reload
5

Delete

Delete the row via its trash icon, confirm the dialog, then re-search the same Employee ID.

asserts toast: "Successfully Deleted" re-search → "No Records Found" API delete → 204
6

Logout / session check

Open the user menu, log out, then request /dashboard/index directly — a real session-invalidation check, not just a one-time redirect.

asserts redirected to /auth/login direct dashboard visit also bounces to /auth/login

03 API validation

Each UI action gets a matching call against reqres.in, and the test asserts the response echoes the same values the UI just showed.

POST/api/users
Mirrors Step 2 — sends employeeId, firstName, lastName right after the UI save.
expect 201 · body echoes all three fields back
PUT/api/users/:id
Mirrors Step 4 — sends the new jobTitle and employmentStatus set in Step 3.
expect 200 · body echoes both fields back
DELETE/api/users/:id
Mirrors Step 5 — deletes the mirrored record right after the UI delete.
expect 204 No Content
One real bug this caught: the client's base URL was originally https://reqres.in/api with request paths starting /users. Per WHATWG URL rules, a leading slash resolves as an absolute path against the origin — so every request silently dropped /api and 404'd. Fixed by keeping the base URL as the bare origin and writing /api/users in full on every call — see src/utils/apiClient.ts.

These three calls run two ways: inline inside the UI scenario above (cross-checking against whatever the UI just did), and as three standalone tests in tests/api/employee-api.spec.ts that create their own data and need no browser at all — for when you want the API layer checked on its own.

04 Data-driven input

Nothing above is hardcoded in the test — it's all read from data/employee.json at run time.

// data/employee.json { "newEmployee": { "firstName": "Ayesha", "lastName": "Karim", "employeeIdPrefix": "QA", "profilePicture": "assets/profile-picture.png" }, "jobUpdate": { "jobTitle": "QA Engineer", "employmentStatus": "Full-Time Permanent" }, "credentials": { "username": "Admin", "password": "admin123" } }

The Employee ID itself isn't in the file — generateUniqueEmployeeId() appends the last 6 digits of the current timestamp to the QA prefix at run time, so repeat runs never collide with a record from a previous run.

05 How to run

npm install npx playwright install chromium
npm test
Everything — the UI scenario plus the 3 standalone API tests. Produces the HTML report and a video recording.
npm run test:ui
Only the UI scenario (tests/employee-lifecycle.spec.ts).
npm run test:api
API tests alone — tests/api/employee-api.spec.ts. No browser launches; finishes in a few seconds.
npm run test:headed
UI scenario with a visible browser window.
npm run test:debug
Opens the Playwright Inspector to step through a run.
npm run report
Opens playwright-report/index.html from the last run.

08 Notes & caveats

opensource-demo.orangehrmlive.com is a shared public demo instance and is occasionally slow to respond — navigation timeouts were raised (90s) and retries: 2 is set in playwright.config.ts to absorb that. A run that needs a retry to pass reflects the target site's own latency, not flakiness in the test logic.
